Project 2 · UI/UX design specification

SentinelSMB - AI-Driven Network Threat Detection and Visualization

Wireframes, user flow, high-fidelity mockups, style guide, accessibility review and requirement mapping for the administrator web application.

Jayman Shrestha · 12 November 2026

1. Purpose of the UI/UX design

Users. The application is used by the IT administrator of a small or medium business (SMB) - usually one person who looks after the network part-time, not a full security operations team. They need to see quickly whether anything is wrong, understand why something was flagged, and know what to do next, without reading raw logs.

UI goal (the look). A dark "security operations centre" theme that is calm by default and makes risk stand out: deep navy surfaces, one cyan → violet → magenta accent gradient, and four severity colours (blue Low, amber Medium, orange High, red Critical) used the same way on every screen, chart and map. A light theme is provided for bright offices and printing.

UX goal (the feel). Every task starts at the dashboard and is at most three clicks deep. The sidebar groups pages by task - Monitor (Overview, Flagged events, Alerts, Incidents, Threat map), Intelligence (Models, Simulator, Data sources, Datasets) and Administration (Notifications, Users, Audit log, Style guide). Security steps (MFA, confirmations for destructive actions, an audit trail) are built into the flow instead of being extra screens.

Design process followed

  1. Wireframes (section 3) - greyscale layouts that fix structure, content hierarchy and navigation.
  2. User flow (section 4) - the wireframes connected into the key task "investigate a threat".
  3. High-fidelity mockups (section 5) - the same screens in the final colours, type and icons, captured from the working prototype.
  4. Style guide (section 6) - palette, typography, buttons, badges, forms and cards; also available inside the app at /style-guide.
  5. Accessibility review (section 7), use case and requirement mapping (section 8) and differences from the report (section 9).

4. User flow - investigate a threat

Each step is named by its use case in the v5 report. The administrator signs in with password and MFA (UC-01), lands on the dashboard (UC-03), opens an alert from the dashboard or the alerts list and reads why it was flagged (UC-04), then works the incident: report, edit, merge and status (UC-04 A3-A7). Incidents can also be reached from the incident timeline (UC-10 A1), and replays started from the Simulator (UC-02) lead to the same alerts and incidents. A Critical alert email (UC-09) links straight to the alert page after sign-in (UC-01 A1). Dashed lines are optional branches and recovery paths.

Labels, keyboard and other checks

  • Every form control now has a visible label tied to it with for/id (severity filters on Alerts and Flagged events, audit-log filters, add-administrator form and file inputs had none).
  • Buttons that only show an icon have an aria-label; per-row buttons on Users name the user ("Disable ops@example.com"). On phones the Sign out text is hidden visually but kept for screen readers (it used to be display:none, leaving the button without a name).
  • Visible 2px focus ring on buttons, links, tabs and fields when using the keyboard (inputs previously had a faint 20% glow only).
  • Form field borders raised from about 1.2:1 to at least 3.4:1 so the field outline is visible (WCAG 1.4.11 non-text contrast).
  • Primary buttons and active tabs use a deeper cyan → violet → magenta gradient so white text is 5.3:1 or more everywhere; the brighter gradient is still used for logos, headings and charts.
  • Severity badges use dedicated text shades (--low-fg, --med-fg, --high-fg, --crit-fg); the vibrant colours are kept for dots, charts and the map. Severity is always written as a word, never colour alone.
  • Charts are announced as images with a description (role="img", aria-label "Chart: ..."); the same numbers are in the tables. Model plots have descriptive alt text instead of file names.
  • Breadcrumbs on the alert page, aria-current on the active nav item and tab, role="search" on filter forms, and a label for the threat-map region.
  • Consistent page structure: one H1 plus a one-line subtitle on every page; labels in a shared .field style; buttons always declare type="submit" or type="button".
  • The threshold control on Models is now a slider kept in sync with the number field.
  • Existing: skip-to-content link, reduced-motion support, Inter font at 14px body, 12px minimum for small text.
  • New v5 screens (Simulator, Incidents, Incident detail, Accept invitation, layout editor, SMS card) use the same tokens and pass the same label and contrast checks; status pills always contain the status word; the replay progress bar is a labelled role="progressbar" and the sensitivity preview is announced with aria-live.

Automated tests (tests/test_accessibility.py) re-check contrast in both themes and fail the build if any page has a form field without a label or a button without a name.
